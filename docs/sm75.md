# XTier on sm_75 (Turing)

This branch runs XTier on **sm_75** hosts (RTX 2080 Ti, T4, RTX A4000): the same SGLang main + XTier plugin, with the
GPU-side features that need a newer card turned off and the few kernels that assume a newer card replaced.

The reference host of this branch: **2x RTX 2080 Ti** (22.5 GB each, sm_75, no BF16 tensor cores, no FP8/FP4 tensor
cores, no TMA, 64 KiB of shared memory per SM), CUDA 13.2, SGLang main, the DeepSeek V4.1 Flash GGUF checkpoint on the
Optane drive.

## What SGLang itself supports

SGLang is not a Blackwell-only framework: its Triton kernels, its loaders and its servers run on Turing, and this host
loads and serves the model with them. But **this model** (DeepSeek V4.1) has parts that assume a newer card, and
SGLang gates them:

| the part | the gate | on sm_75 |
|---|---|---|
| the fused Q/K RoPE (a JIT kernel) | BF16 only | the Triton RoPE takes over (`packs/deepseek_v4/rope.py`) |
| the MHC pre/post-mix and the DSA indexer | TileLang, the MMA shapes need sm_80+ | SGLang's own torch / Triton paths (`packs/deepseek_v4/tilelang.py`) |
| the KV cache dequantizer | the fp8 pointer needs sm_89, the V4.1 path is gated to sm_100 | the e4m3 bytes are converted with bit math (`packs/deepseek_v4/kv_fp8.py`) |
| the attention (FlashMLA) | "only supported on SM90a and SM100f" | SGLang's portable gather-and-einsum path (`packs/deepseek_v4/attention.py`) |
| the sparse prefill | the same FlashMLA kernel | the dense path over the same selected rows (`packs/deepseek_v4/attention.py`) |
| the DSA indexer's sparse path | `is_sm100_or_newer()` | SGLang falls back to the dense path by itself |
| the FP8 / FP4 packs, the W8A8 configs | sm_89+ (FP8), sm_100+ (FP4) | off (`xtier/packs/__init__.py`'s `supported()` gates every one of them) |
| the compressed KV's FP4 fake quant (fused with the tail RoPE) | the kernel casts to NVFP4's e4m3, which Triton emits on sm_89+ | SGLang's own torch path (`packs/deepseek_v4/fp4_rope.py`) |
| the DSA indexer and the KV compressor | their weights are BF16 whatever the model's dtype is | the activations are cast to BF16 around their projections (`packs/deepseek_v4/dtypes.py`) |
| the BF16 GEMM with an FP32 output (the router, the compressor) | torch refuses it below sm_80 | the operands are upcast (`packs/deepseek_v4/dtypes.py`) |

## What the branch changes

* `xtier/packs/__init__.py` - one place that answers "does this card have (major, minor)?" (`supported()`); every pack
  feature asks it before it installs, and the log says what is off and why.
* `xtier/packs/deepseek_v4/rope.py` - the JIT RoPE is BF16 only; on a card without BF16 tensor cores the activations are
  FP16, so the patch calls SGLang's Triton RoPE (`apply_rotary_emb_triton`) for the non-BF16 case.
* `xtier/packs/deepseek_v4/kv_fp8.py` - the K cache holds the e4m3 bytes of the nope dims; the hardware conversion needs
  sm_89, so the patch loads the bytes as uint8 and converts them with bit math (the same values, see
  `tests/deepseek_fp8_kv_check.py`).
* `xtier/packs/deepseek_v4/attention.py` - the DSV4 attention runs in the FlashMLA CUDA kernel, which needs sm_90+; the
  patch points the call at SGLang's own portable path (the gather-and-dequantize plus einsum of `flash_mla_sm120`, the
  same numbers, in PyTorch) and turns the sparse prefill off so the prefill takes the same path.
* `xtier/packs/deepseek_v4/dtypes.py` - the attention's `wo_a` projection keeps its weight in BF16 (its FP8 path is off
  on such a card) while the activations may not be BF16; the patch casts between the two around the grouped matmul. The
  DSA indexer and the KV compressor keep BF16 weights upstream whatever the model's dtype is; their projections take the
  activations in BF16, so the index keys and the queries stay BF16, as the stored keys are. The BF16 GEMM with an FP32
  output (the router, the ratio-2 compressor) needs sm_80: the pack upcasts the operands instead (the same numbers).
* `xtier/packs/deepseek_v4/fp4_rope.py` - the fused tail RoPE and FP4 fake quant of the compressed KV casts to NVFP4's
  e4m3, which Triton emits only on sm_89 and newer; on such a card the pack points the call at SGLang's own torch path
  (the same numbers, in PyTorch).
* `xtier/packs/deepseek_v4/tilelang.py` - the TileLang kernels of the pack need sm_80+; on Turing they are turned off and
  SGLang's own paths take over.
* `xtier/backend/gguf_names.py` - the checkpoint's name map: the shared expert's three tensors (the gate, the up and the
  down) are in it. Without them the model's shared expert keeps uninitialized weights: the hidden state turns into NaN
  and the engine rejects the routing weights.
* `configs/sm75-2x2080ti/` - the run script and the console for this host.

## The run script

```
MODEL=/home/userroot/work/model/ds41-gguf PORT=18190 \
configs/sm75-2x2080ti/run-xtier-sm75.sh
```

The script sets what the card needs:

* `FLASHINFER_CUDA_ARCH_LIST=7.5`, `TVM_FFI_CUDA_ARCH_LIST=7.5` - the JIT kernels compile for this card (the script
  reads the compute capability of the device, so the same script works on the Blackwell hosts);
* the CUDA toolkit - the JIT compilers need a toolkit whose compiler and headers are the same version (the CCCL
  headers refuse a mix: "CUDA compiler and CUDA toolkit headers are incompatible"), so the script picks the first
  consistent toolkit it finds (`XTIER_CUDA_ROOT` names one);
* `--dtype bfloat16` - the checkpoint's dtype. The hyper-connection's residual stream needs BF16's range: it carries the
  layer outputs and grows with the depth, and in FP16 it overflows (65504) at layer 23. The card has no BF16 tensor
  cores, so the GPU kernels emulate BF16 (the CPU engine's contract is BF16 anyway);
* `--kv-cache-dtype fp8_e4m3` - the K cache is the packed uint8 format (the model requires it), and the pack's
  patch makes the dequantization work without the hardware conversion;
* `--chunked-prefill-size 256` - the portable attention gathers the KV rows of the whole chunk (1.75 GiB for 1024
  rows), and the card has 1.25 GiB free after the weights and the KV cache, so the chunk is small;
* `--disable-cuda-graph` - the decode graph pool does not fit next to the weights on a 22.5 GB card;
* `--cuda-graph-backend-prefill disabled` - the prefill's CUDA graph is off;
* `XTIER_ISA=avx2` - the host is Broadwell (AVX2, no AVX-512 BF16), so the CPU engine uses the AVX2 kernels;
* `XTIER_GSQ_PACK` - the GSQ pack (the MoE experts in the format the CPU engine reads) on the Optane drive;
* `XTIER_COLD=1` - the cold pool: the experts of the RAM slots, the rest read from the Optane drive when a forward
  routes to them (the checkpoint's own files are the store, read with O_DIRECT);
* `XTIER_CACHE_SLOTS=8` - an 11 GB card holds few hot experts, a few slots per layer instead of the 155 of the
  RTX PRO 5000.

## The card's memory

The DeepSeek V4.1 Flash checkpoint is 18.56 GB of weights (the dense parts: the attention, the shared experts, the
embeddings); the routed experts live in the CPU engine (the GSQ pack on the Optane drive). That leaves 2.84 GB for the
KV cache and the activations, which is why the decode graph is off and the context is short.

The Engram table (110 GB, IQ4_NL, beside the shards) is not read: this checkpoint's `engram_layer_ids` is empty, so the
model has no Engram layer and the file stays on the drive.

## What runs on the host

* the load: the four GGUF shards give the dense weights (the attention, the shared experts, the router, the
  hyper-connection), the GSQ pack gives the routed experts (the IQ rows the CPU engine reads), and the cold pool keeps
  269 of the 384 experts of a layer in RAM and the rest on the drive (`XTIER_COLD=1`);
* a request: the prefill and the decode go through the engine, the GPU's hot expert cache and the cold pool; the
  answer is right ("2+2 equals 4.", "Tokyo.") and the hyper-connection's residual stream stays bounded over the 40
  layers (it needs BF16's range: in FP16 it overflows at layer 23);
* the speed: about 0.4-0.7 tok/s, bound by the emulated BF16 dot products, the CPU engine's MoE and the PyTorch
  attention - not by the memory.

## What is not done on sm_75

* the packed FP4 experts (NVFP4/MXFP4) are not decoded in hardware: the packs that need it are off;
* the W8A8 FP8 configs and the FP8 draft head are off;
* the Qwen hyper-connection mix overlap (it needs TMA) is off;
* the attention runs in PyTorch (the FlashMLA kernel needs sm_90+): the same numbers, but the decode is slow.
