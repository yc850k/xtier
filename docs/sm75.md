# XTier on sm_75 (Turing)

This branch runs XTier on **sm_75** hosts (RTX 2080 Ti, T4, RTX A4000): the same SGLang + XTier plugin, with the
GPU-side features that need a newer card turned off and the few kernels that assume a newer card replaced.

It is **main (the RTX 30/40 series work) plus the Turing tier**: the upstream line for the cards below sm_90 is
taken over as it is (the Triton sparse MLA, the mHC split-K, the FP8 in software), and Turing gets the one layer the
Ampere path does not need: **BF16 has no tensor cores here**, so the model runs in FP16 and the hyper-connection's
residual stream in FP32.

The reference host of this branch: **2x RTX 2080 Ti** (22.5 GB each, sm_75, no BF16 tensor cores, no FP8/FP4 tensor
cores, no TMA, 64 KiB of shared memory per SM), CUDA 13.2, SGLang 0.5.22, the DeepSeek V4.1 Flash GGUF checkpoint on the
Optane drive.

## The dtype layer (the part the Ampere path does not need)

On sm_86 and sm_89 the model runs in BF16, as its kernels were written. On Turing there is no BF16 tensor core: a
BF16 dot product is emulated by the software (measured here: 6.2 TFLOP/s against FP16's 106, and Triton's BF16
`tl.dot` is worse still). So the model runs in **FP16**, the dtype the card's tensor cores take, and the layers that
need more range than FP16 has get it:

| what | the dtype | why |
|---|---|---|
| the activations and the dot operands | **FP16** (BF16 from sm_80 on) | the card's tensor cores: `arch.dtype()`, `arch.dot_dtype()` |
| the hyper-connection's residual stream | **FP32** (below sm_80) | it carries the layer outputs and reaches 284672 over the 40 layers, past FP16's 65504: `packs/deepseek_v4/dtypes.py` keeps it in FP32 (`_post_fp32`, `_combine_fp16`, `_norm_fp32`) |
| the CPU engine's contract | **BF16** | unchanged: the activations are converted when they are staged for it (`xtier/backend/kernels.py:_pack`) |
| the BF16 weights upstream keeps (the DSA indexer, the KV compressor) | BF16, the activations cast around them | the weights are BF16 whatever the model's dtype is: `packs/deepseek_v4/dtypes.py` |

The kernels that upstream wrote for a BF16 model follow the activation's dtype now (`xtier/packs/deepseek_v4/wo_a.py`,
`w8a16.py`, `engram_gather.py`, the Engram row buffers, `kv_fp8.py`; `xtier/packs/qwen4_exp/ple_rows.py`,
`qsa_fp4.py`; `xtier/packs/minimax_m3/kv_fp4.py`): a `DT` constexpr (the Triton dtype of the activations) instead of
a hardcoded `tl.bfloat16`, and the buffers take the model's dtype.

## The codecs (the dequantization in software)

Upstream's method for the cards below sm_89/sm_100 is the one of this branch: **the checkpoint's format is not
touched, the values are converted in software** - the same numbers as the hardware instructions, bit for bit.

* `xtier/backend/fp4.py` holds the bit math: the E2M1 decode (`e2m1_f16`), the E4M3 decode (`e4m3_f32`) and the E4M3
  encode (`e4m3_bits`).
* `xtier/arch.py` is the one entry point for them, with the hardware-software choice per call: `arch.e4m3_f32(code)`
  takes the card's path, `arch.e4m3_f32(code, HW)` the caller's. `XTIER_FP4_DECODE=hw|soft|auto` and
  `XTIER_FP8_DECODE=hw|soft|auto` pick the default, so the two paths can be compared on the same GPU.
* the checks: `tests/fp4_decode_check.py` (the E2M1 table and the pool's kernels), `tests/fp8_decode_check.py` (the
  E4M3 values against torch's `float8_e4m3fn`), `tests/fp8_encode_check.py` (the E4M3 rounding against the hardware
  conversion, or against torch's own cast where Triton has no `float8e4nv`), `tests/ds_fp8_soft_check.py` (the Engram
  gather and the FP4 fake quant of the compressed KV).

## What stays off on the card

| the part | the gate | on sm_75 |
|---|---|---|
| the fused Q/K RoPE (a JIT kernel) | BF16 only | the Triton RoPE takes over (`packs/deepseek_v4/rope.py`) |
| the MHC pre/post-mix and the DSA indexer | TileLang, the MMA shapes need sm_80+ | SGLang's own torch / Triton paths (`packs/deepseek_v4/tilelang.py`); the mHC split-K for the 20480 hidden size (TileLang) is off too |
| the MHC's Sinkhorn | the TileLang kernel returns NaN here | SGLang's Triton port (`packs/deepseek_v4/tilelang.py`) |
| the KV cache dequantizer | the fp8 pointer needs sm_89 | the e4m3 bytes are converted with bit math (`packs/deepseek_v4/kv_fp8.py`) |
| the attention (FlashMLA) | "only supported on SM90a and SM100f" | the Triton sparse MLA over the same pages (`packs/deepseek_v4/sparse_mla.py`), SGLang's portable path as the fallback |
| the 32x32 block FP8 projections | the FP8 tensor cores (sm_89) and Triton's `float8e4nv` | the weights keep SGLang's FP8 layout and are dequantized in software (`packs/deepseek_v4/w8a16.py`) |
| the FP8 / FP4 packs, the W8A8 configs | sm_89+ (FP8), sm_100+ (FP4) | off (`xtier/packs/__init__.py`'s `supported()` gates every one of them) |
| the compressed KV's FP4 fake quant | the kernel casts to NVFP4's e4m3, which Triton emits on sm_89+ | SGLang's own torch path (`packs/deepseek_v4/fp4_rope.py`) |
| the TMA features (the Qwen hyper-connection mix overlap) | sm_90+ | off |

## The Triton sparse MLA (the attention below sm_90)

Upstream's below-SM90 line (main, PR #10) replaces the FlashMLA kernel with a Triton sparse MLA over SGLang's packed
FP8 pages: FlashMLA is built for sm_90 / sm_100 / sm_103 only, so the cards below that could not run DeepSeek V4.1 at
all. The kernel is taken over from there (`xtier/packs/deepseek_v4/sparse_mla.py`) with the three changes Turing
needs:

* the dot products in FP16, not BF16: Turing has FP16 tensor cores and no BF16 ones, so a BF16 dot is emulated;
* the tiles smaller: Turing's SM has 64 KiB of shared memory, the upstream's tiling is sized for Hopper's 99 KiB
  (16 keys and 16 heads per program instead of 32);
* the FP8 values decoded with this branch's own codec (`xtier/backend/fp4.py`), exactly as upstream does on the cards
  without the FP8 conversion instruction.

The PyTorch path stays the fallback (the kernel does not fit a card, or `XTIER_SPARSE_MLA=0` keeps it).
`tests/sparse_mla_check.py` checks it against a plain reference (the max error 2.7e-4, the lse error 4.8e-7).

## The hot experts in the VRAM, and what the GPU computes

The design of the project: the hot experts live in the card's memory and the GPU computes them; the CPU engine takes
the rest. On this host that is limited by the card, not by the code:

* the dense weights take **12.1 GB of the 22.5 GB** of a card (the GGUF's dequantized weights, measured at the load),
  so about 5.8 GB are left for the KV cache and the hot experts;
* a GSQ expert is ~7.7 MB of IQ bytes, and a layer's experts are in their own slots: a slot per layer costs 7.7 MB x
  the 40 layers, so the whole VRAM holds **12 experts of the 384 of a layer**; the rank's slice of an expert (the
  rows of the gate and the up the rank owns, the down whole) is 5.2 MB, so the same VRAM holds **26 experts of the
  384 of a layer** (`XTIER_CACHE_SLOTS=26`);
* the KV cache takes the rest (`--mem-fraction-static 0.727`: the context on this host is a few hundred tokens, and the
  KV cache of the 32K context would need 27 GB).

What the GPU then computes:

* the **decode** (up to `XTIER_DECODE_MAX=64` tokens a call): the routes of the cached experts are computed on the GPU
  (their IQ blocks decoded in the tile kernels, `xtier/backend/gsq_gpu.py`), the engine computes the rest, and the two
  halves are added;
* the **batched prefill** (more than 64 tokens): the same, with the routes of one expert grouped into tiles
  (`xtier/cache/gsq_pool.py`: `prefill`) - the GPU's part and the CPU engine's part run at the same time and their sums
  are added. Before this, a GSQ prefill went to the CPU engine entirely.

The measured split on a Turing card (81 prompt tokens, 486 routes, `XTIER_TIMING=1`): the GPU's part of the cached
routes takes **1.6 ms**, the upload of the experts that are not in the VRAM **212 ms**, the CPU engine's part of the
rest **984 ms** - the GPU decodes the same IQ blocks about a thousand times faster, so what is left of the CPU engine's
time is the wall. The share the GPU gets is the VRAM's share of the experts (12 of 384 a layer: 12% of the routes of a
spread prompt, more of a typical one).

**The GPU decodes the experts.** The pool's decode uploads the experts the call routes to (the ones that are not in
the VRAM) over PCIe into the scratch arena the layers share, and computes them on the card; the packing kernel marks
those routes for the GPU, so the CPU engine sees none of them. The server's own counter says so: **the GPU serves 100%
of the distinct experts a call routes to** (`hit 1.000`), and the engine's part of a layer call is **7 microseconds**
(the AVX2 IQ decode used to be the whole call). The residency follows the traffic: the adaptive policy swaps the
experts with the most routes into the VRAM and the least routed out of it (32 swaps in the first round here).

**The cards' power**: the prefill's GPU burst (the upload, the IQ decode of the batch's experts, the grouped GEMMs)
draws **185-189 W a card** (the RTX 2080 Ti's idle is ~30 W); between the bursts the cards idle at 60-75 W with a 6-20%
utilization, because the CPU engine's share of the MoE (the experts that do not fit in the VRAM) is the wall: the
engine decodes the IQ blocks at about 0.5 GB/s, the GPU at about 90 GB/s, so every expert that moves to the GPU is
roughly a hundred times cheaper - and what stops it is the 22.5 GB of VRAM (the weights take 12.9 GB of it).

**The batched prefill uploads the experts it needs.** The experts a batch routes to that are not in the VRAM are moved
over PCIe once - from the engine's RAM slot when the cold pool has it there (fast), else from the checkpoint's files
(the pack's mapping) - into a scratch arena the layers share (`XTIER_GSQ_PREFILL_UPLOAD=64` slots), and the GPU decodes
and multiplies them there. The CPU engine then sees only the routes of the experts that did not fit in the scratch.
`tests/gsq_prefill_check.py` checks that the engine computes nothing in that path and that the numbers are the
engine's (the relative L2 2.7e-4, the FP16 rounding).

## The decode's speed: what the GPU does and what the host costs

The decode is the part that matters for the talk, and on this host it is a chain of small things. The measured
numbers below are the ones the server itself logs (`XTIER_TIMING=1`, the per-layer lines) on the reference host
(2x RTX 2080 Ti, TP=2, the DeepSeek V4.1 Flash GGUF on the Optane), with the rate measured on the streamed tokens
(the prefill excluded: it is 50 s of its own on this host).

| the change | the decode |
|---|---|
| the start of this work (the pool with the whole experts, the uploads draining the decode stream) | **0.5-0.9 tok/s** |
| the rank's slice of the intermediate (the TP split, below) | (a correctness fix, the same speed) |
| the uploads on their own stream (the decode stream waits with an event) | **1.65 tok/s** |
| the rank's slice of the bytes (the gate and the up rows only) | **2.2 tok/s** |
| the swaps reading the checkpoint's files (the residency follows the traffic) | the hit rate 8% -> 33% |
| the cold pool following the GPU's traffic (the routed experts are read into the engine's RAM) | **2.5-2.9 tok/s** |
| the cold pool's slots holding the rank's slice (the same bytes the GPU reads) | **2.9-3.0 tok/s** |
| the IQ2_XXS decode in three dimensions (the codes loaded once per group) | the first token 26 s -> **17 s** |
| a bigger cold pool (the fraction 0.55) | **3.0 tok/s** |

**The tensor-parallel split was wrong, and it was silent.** The pool computed the *whole* expert (the intermediate of
2304) while SGLang sums the two ranks' MoE outputs: each rank's contribution was the full expert, so the routed branch
was counted twice. The evidence is the logprob of a fixed prompt: the pool's path scored **-188.6** where the CPU
engine alone scored **-168.1** (the same prompt, the same weights). The pool now computes the rank's own slice of the
intermediate (the rows of the gate and the up, the columns of the down), exactly like the engine does with its
`gsq_split`: the pool's path scores **-169.7** (the FP16 rounding against the engine's BF16), and the copy test still
matches 100%. The same slice is what travels over PCIe now (the gate and the up rows the rank owns), which is why the
upload's bytes fell by a third.

**The uploads used to drain the decode stream.** Every expert that was not in the VRAM was staged in pinned memory and
copied with a `cudaStreamSynchronize` per tensor - sixteen times a layer, and each of them drained the whole decode
pipeline. The copies now run on their own stream (the decode stream waits for them with an event, and the copy stream
waits for the decode before it overwrites the arena). That is the 3x between the first row and the second.

**The residency follows the traffic, but only now.** The adaptive policy swaps the most routed experts into the VRAM and
the least routed out of it, but a swap could only read the expert's bytes from the engine's RAM slot: on this host
that is 115 of the 384 experts of a layer, so 87% of the swaps were skipped (`swaps_no_ram`). A swap now reads the
expert's bytes from the checkpoint's own mapping when the engine's RAM does not have them, and the residency follows
the routes the decode really makes (the hit rate 8% -> 33%, the top 26 experts of a layer covering about a third of the
routes).

**The engine's RAM holds the rank's slice.** The RAM pool kept the whole expert (7.7 MB) while the rank only ever
needs its slice of it (5.2 MB: the rows of the gate and the up, the down whole), so the same RAM held 115 experts of a
layer while the traffic touched 116-125 of them: the pool's LRU thrashed and the drive was read on every call. The slots
hold the rank's slice now (the engine reads the slot's rows and the down's columns, exactly like the GPU does), so the
same RAM holds **172** experts of a layer, the working set fits, and the drive is read once (the uploads' file traffic:
0). The RAM the pool takes drops by a third as well (29 GB less on this host: the pool's 82 GB instead of 111 GB, and
the page cache gets the room). The engine's own numbers do not change: the CPU engine's path scores the same logprob
bit for bit (-168.0674) with the sliced slots.

**The engine's RAM follows the GPU's traffic too.** The upload used to read the experts it needed from the
checkpoint's files, because the engine's RAM pool kept what the *profile's* ranking said (the engine itself never
routed to them: the GPU served every route), so the bytes came from the drive on every call. The pool now asks the
cold pool to make the experts it routes to resident before the upload - the same call the engine makes before it
computes: the ones that are not in RAM are read from the store, the coldest resident leaves. The RAM then holds what
the GPU is asked for, the upload copies the bytes from the pinned slots, and **the checkpoint's files are not read any
more in the steady state** (the uploads' file traffic: 748 MiB per 192 calls a layer -> 0; the pinned RAM's takes it).

### What the host costs now, and why 15 tok/s does not fit on this card

The decode is a chain: the router's top-k (on the GPU), then the routed experts' bytes (the PCIe upload), then the IQ
decode (on the GPU). Per layer call (the server's own counters, 64 calls a window):

| the part | the time |
|---|---|
| the GPU's IQ decode of the routed experts (the gate/up in two launches, the down) | **2.1-3.2 ms** (85-130 ms a token) |
| the upload of the experts that are not in the VRAM (the file reads at 2-3 GB/s, the RAM at 12) | **6-7 ms** (250-280 ms a token) |
| the selection of the routed experts (the CPU's part) | 0.6 ms |

The GPU's part is the IQ decode of the routed experts: 4.2 G values a token (the rank's slice of the gate, the up and
the down of every routed expert of the 40 layers). The decode alone runs at about 122 G values/s, but the kernel also
multiplies the decoded block with the activations, and there the tensor cores' shape hurts: their M is 16 while a decode
call has **one** token, so their dot would do sixteen times the work. The one-token call therefore multiplies plainly
(the FMA path, in FP32): the GPU's time a layer call falls from 2.4 ms to **1.5 ms** (the whole MoE of a token: 96 ms ->
62 ms).

The three parts of the token, measured:

| the part | the time | what bounds it |
|---|---|---|
| the GPU's IQ decode of the routed experts | **62 ms** | the card's speed at the software decode (the decode alone 122 G values/s, the multiply that goes with it) |
| the drive's reads of the experts the RAM does not hold | **~160 ms** | the RAM's budget: the two ranks each need their own slice of every expert (71 GB of the host's 141), so the cold pool holds 173 of the 384 experts of a layer and the rest come from the Optane at 2-3 GB/s |
| the CPU's Python and the GPU's waits between them | **~100 ms** | the router's ids have to reach the CPU before the upload can start, and the upload's bytes have to reach the card before the kernels can run |

That is the ~340 ms a token this host's memory and card allow: **about 3 tok/s**, which is what it measures. The 15 tok/s
goal is 67 ms a token, less than the IQ decode alone costs here. It needs either a different card (a Blackwell-class one
decodes the same IQ blocks several times faster) or a checkpoint whose experts fit in the VRAM (no drive reads at all),
and even then the CPU's share of the token has to come down - a CUDA graph would take the Python out of the loop, but the
upload's addresses change from call to call, so the graph cannot capture it.

The other half of the token time is the CPU: the model worker spends about 3.5 ms a layer in the Python, of which the
XTier method's own share is 2.1 ms (the uploads' selection and the copies, which wait for the PCIe), and the scheduler's
thread is busy the whole time. The decode is therefore a ping-pong between the two: the router's ids have to reach the
CPU before the upload can start, and the upload's bytes have to reach the card before the GPU's kernels can run. A CUDA
graph would take the Python out of the loop, but the upload's addresses change from call to call, so the graph cannot
capture it.

The pool's decode call is the CPU's biggest share (about 8 ms of CPU a layer call, of which the upload's is 1.6 ms):
most of it is not the Python but the kernel's own time for the drive's reads (the O_DIRECT copy into the RAM slots),
and the rest is the launches and the waits. The cold pool's reads are the third cost: the experts the RAM does not
hold are read from the drive at 2-3 GB/s. The
RAM holds 173 of the 384 experts of a layer (the fraction 0.55, the slices) and the traffic touches 116-125 of them, so
the pool's LRU still churns a little (1.8 ms a layer call; 2.9 ms with a smaller pool, the fraction 0.65). The pool's
RAM is 71 GB of the unit's 141 (the page cache keeps 37 GB of the rest). The 15 tok/s goal is 67 ms a token: it does not fit
on a Turing card, whatever the host does around it (the dense weights alone are 12 GB a card, 27 ms a token at its
bandwidth). What the host can be made to give is the part around the kernels, and that is what the three changes above
do: the decode went from 0.5-0.9 tok/s to 2.9-3.2 tok/s (a long decode settles at 2.6-2.7: the context grows
and the attention costs more), and the rest of the time is the PCIe traffic of the experts
that the VRAM does not hold (the traffic of a decode is spread over 116 experts of a layer in 16 calls, and the top 26
of them cover a third of the routes) and the per-layer kernel launches (the CPU is the pipeline's clock: the GPU idles
between the fifty and a hundred launches a layer, and a CUDA graph cannot be used here - the upload's addresses
change from call to call).

The prefill is the other half of the wall: the experts a batch routes to are uploaded and decoded on the GPU
(`XTIER_GSQ_PREFILL_UPLOAD=128` slots of the scratch arena), so the CPU engine's part of a prefill is 1-20 ms a layer
instead of 200-660 ms; what is left of the prefill's time is the drive (the experts' bytes at 2-3 GB/s) and the GPU's
IQ decode of the batch's experts. The prefill's tiles are small on purpose (`XTIER_GSQ_PREFILL_TILE_M=8`): a tile of
32 routes and 16 rows does not fit in the registers (the decode's kernel uses 255 of them, the cap), and the small
tile is worth twice the prefill's speed. The IQ2_XXS decode itself is in three dimensions (the row, the group of
eight values, the value in the group): a group's codes and scales are the same for its eight values, so they are
loaded once for the group instead of once for every value (six loads per value against one and a half) - the loads
are what the kernel spends its time on. The two together take **the time to the first token of a 78 token prompt from
47 s to 17 s** (the decode is unchanged: its kernel is bound by the magnitudes' gather, not by the codes).


## The memory budget (the RAM the engine holds)

The engine's RAM holds the hot experts (the cold pool's resident set); the rest are read from the Optane drive when a
forward routes to them (the store's own files, O_DIRECT). The measured sizes:

| what | how much |
|---|---|
| the whole expert set (384 experts x 40 layers x 7.74 MB) | **118.9 GB** |
| the host's RAM | 141 GB (+8 GB of swap) |
| the engine's other buffers and the page cache | ~8 GB (the rest of the page cache is reclaimable) |

**The expert weights are not distributed over the TP ranks**: each rank keeps its own copy of the experts it computes
(the split narrows what is computed, not what is stored), so with two ranks the RAM holds the set twice. Measured per
rank (the process' RSS): the cold pool's experts (the resident set) plus the engine's own buffers, about 10 GB a rank.
The cold pool's fraction follows the rank count, and the launcher picks it:

| the ranks | the cold fraction | the experts in RAM | the RAM per rank | in total |
|---|---|---|---|---|
| one (`TP=1`) | 0 (the whole set in RAM, the drive keeps the store's copy) | 119 GB | 129 GB | 129 GB |
| two (`TP=2`) | 0.65 (115 of 384 experts a layer) | 36 GB | 46 GB | 92 GB |

The fraction 0.3 (269 experts a layer) put 83 GB of experts in a rank, 167 GB for the two: the OOM killer took the
server at 140+ GB. The fraction 0.54 measured 135 GB of the 141 GB - too close. The hot experts in the VRAM are what
takes the pressure off the RAM: the cold pool gives its RAM slots to the experts *after* the ones the GPU cache holds
(12 a layer here), so every slot in the VRAM is one the RAM does not have to keep.

The engine's RAM is registered with CUDA (`XTIER_GSQ_PIN=1`) so that the GPU reads it at the full PCIe speed (the
upload of a batched prefill copies the experts' bytes from there). The registration is bounded by the memlock limit
(18.5 GB here, `ulimit -l`): what does not fit stays pageable and the upload falls back to the driver's staging
buffer.

## The scope of this branch

Only the sm_75 dequantization and computation: the codecs (software E2M1/E4M3), the dtype layer (FP16 activations,
the FP32 residual), the kernels that need a Turing shape (the sparse MLA's tiles, the IQ decode in the batched
prefill), the gates and the host's configuration. The inference framework of main is not touched: no hook on SGLang's
model or arguments, no change to the MoE dispatch, the mailbox or the engine's contract.

## The run script

```
MODEL=/home/userroot/work/model/ds41-gguf PORT=18190 TP=1 \
configs/sm75-2x2080ti/run-xtier-sm75.sh
```

The script sets what the card needs:

* `FLASHINFER_CUDA_ARCH_LIST=7.5`, `TVM_FFI_GPU_ARCH_LIST=7.5` - the JIT kernels compile for this card (the script
  reads the compute capability of the device, so the same script works on the Blackwell hosts);
* the CUDA toolkit - the JIT compilers need a toolkit whose compiler and headers are the same version (the CCCL
  headers refuse a mix: "CUDA compiler and CUDA toolkit headers are incompatible"), so the script picks the first
  consistent toolkit it finds (`XTIER_CUDA_ROOT` names one);
* `--dtype float16` - the model's dtype: the card's (the dot products are FP16). The hyper-connection's residual
  stream, which needs more range, is kept in FP32 by the pack. The *weights* are dequantized into what the card
  computes: the GGUF's IQ blocks at load time, the FP8 and FP4 ones in the kernels, with bit math;
* `--kv-cache-dtype fp8_e4m3` - the K cache is the packed uint8 format (the model requires it), and the pack's patch
  makes the dequantization work without the hardware conversion;
* `--chunked-prefill-size 256` - the portable attention gathers the KV rows of the whole chunk (1.75 GiB for 1024
  rows), and the card has 1.25 GiB free after the weights and the KV cache, so the chunk is small;
* `--disable-cuda-graph` - the decode graph pool does not fit next to the weights on a 22.5 GB card;
* `XTIER_ISA=avx2` - the host is Broadwell (AVX2, no AVX-512 BF16), so the CPU engine uses the AVX2 kernels;
* `XTIER_GSQ_PACK` - the GSQ pack (the MoE experts in the format the CPU engine reads) on the Optane drive;
* `XTIER_COLD=1` - the cold pool: the experts of the RAM slots, the rest read from the Optane drive when a forward
  routes to them (the checkpoint's own files are the store, read with O_DIRECT);
* `XTIER_CACHE_SLOTS=12` - the hot experts of a layer in the VRAM (12 of its 384: the dense weights take 73% of
  the card, so the hot experts and the KV cache share the rest);
* `--mem-fraction-static 0.76` - the KV cache takes what the hot experts leave (the context on this host is a few
  hundred tokens; the weights alone need 0.727);
* the GPU prefill's tiles: `XTIER_GATE_BN=64 XTIER_GATE_BK=64 XTIER_GATE_LAUNCH=4,2` and the same for the down
  projection - they fit Turing's 64 KiB of shared memory (the Blackwell hosts run 128 x 64 with 3 stages);
* the batched prefill of the GSQ path: `XTIER_GSQ_PREFILL_TILE_M=32` (the routes of one expert per tile) and
  `XTIER_GSQ_PREFILL_TILE_N=16` (the rows of a tensor per program).

## The card's memory

The DeepSeek V4.1 Flash checkpoint is 18.56 GB of weights (the dense parts: the attention, the shared experts, the
embeddings); the routed experts live in the CPU engine (the GSQ pack on the Optane drive). That leaves 2.84 GB for the
KV cache and the activations, which is why the decode graph is off and the context is short.

The Engram table (110 GB, IQ4_NL, beside the shards) is not read: this checkpoint's `engram_layer_ids` is empty, so the
model has no Engram layer and the file stays on the drive.

## What runs on the host

Measured on the reference host (2x RTX 2080 Ti, TP=2, the GGUF checkpoint on the Optane drive, the FP16 model with the
FP32 residual):

* the load: the four GGUF shards give the dense weights (the attention, the shared experts, the router, the
  hyper-connection), the GSQ pack gives the routed experts (the IQ rows the CPU engine reads) - 384 experts a layer in
  0.35 s each - and the cold pool keeps 77 of the 384 experts of a layer in RAM and the rest on the drive
  (`XTIER_COLD_FRACTION=0.8`); the GPU's hot expert cache takes 320 experts per rank (0.7 s). The server is ready in
  about three minutes (the weights 167 s, the engine 205 s);
* both cards are full: 20.9 GB of the 22.5 GB each (the dense weights, the KV cache, the hot experts and the
  activations);
* a request (an 81-token prompt, 64 tokens out): 198.7 s the first time and 187.1 s the second (the same answer,
  temperature 0): the prefill runs at 0.4-1.35 tok/s (the cold pool reads the experts from the drive), the decode at
  0.24-0.44 tok/s (SGLang's own counters, growing with the context);
* the answer is right ("The sky is blue because Rayleigh scattering redirects short wavelengths - especially blue
  light near 450 nm - more strongly than longer wavelengths..."), the residual stream stays bounded over the 40
  layers (no NaN in the log, the engine accepted the routing weights);
* the three tiers are in the log: the GPU's cache (320 GSQ experts uploaded per rank), the CPU engine (the layers'
  experts) and the cold pool (the experts in RAM and the rest on the drive).

## Two cards (TP=2)

`configs/sm75-2x2080ti/run-xtier-sm75.sh` runs the model over both cards (`TP=2`, the default): each rank holds half
of the dense weights, half of the KV cache and its own CPU engine over its own group of NUMA nodes
(`XTIER_TP_NODES=auto`, the threads from `tools/cpu_budget.py --tp 2`).

Two things the Turing host needs for it:

* the GSQ split: the rank's part of every expert is a slice of its intermediate (1152 of 2304 values), so the engine
  decodes the blocks that overlap the slice and uses only its columns (the same numbers). The engine's `full_inter` is
  the expert's whole intermediate, not the rank's part;
* the host memory: each rank keeps a copy of the experts it holds in RAM (the split narrows what is computed, not what
  is stored), so the cold pool has to hold twice as much on the drive: `XTIER_COLD_FRACTION=0.8` (76 of 384 experts in
  RAM per layer, 27.7 GB per rank) fits the unit's 128 GB cap with the two ranks. At 0.3 the two ranks need 195 GB and
  the cgroup throttles them (the load never finishes).

The alternative to TP=2 is the second card as the hot-expert pool (`XTIER_GPU2_SLOTS`, `xtier/cache/second.py`).

## The checks

The checks that need no model run on the card:

| the check | what it shows on sm_75 |
|---|---|
| `tests/sm75_gpu_check.py` | the cache's gate/up (NVFP4 and MXFP4 experts) and the grouped GPU prefill against an FP32 reference, in the card's dtype (FP16): the relative L2 2.1e-4 and 3.0e-4 |
| `tests/fp4_decode_check.py` | the software E2M1 decode against the table (0 differences over 256 bytes); the hardware path does not exist here |
| `tests/fp8_decode_check.py` | the software E4M3 decode against torch's `float8_e4m3fn` (0 differences over 256 bytes) |
| `tests/fp8_encode_check.py` | the software E4M3 encoding against torch's own cast (0 differences over 9.4 million values) |
| `tests/ds_fp8_soft_check.py` | the software Engram gather against the pool's bytes, and the rebuilt FP4 fake quant against SGLang's torch path (bitwise equal) |
| `tests/ds_sparse_mla_check.py`, `tests/sparse_mla_check.py` | the Triton sparse MLA against a plain reference |
| `tests/ds_w8a16_check.py` | the block FP8 projections weight-only (the FP8 einsum and the dequantize + cuBLAS path) against FP64: the worst relative error 3.1e-4 |
| `tests/deepseek_fp8_kv_check.py` | the FP8 KV cache dequantizer, bit for bit (0 mismatches) |
| `tests/qsa_decode_check.py`, `tests/qsa_fp8_check.py` | the Qwen QSA decode and the software FP8 KV reads (the pool's own bytes as the reference below sm_89) |
| `tests/glm_indexer_torch_check.py` | the GLM indexer in torch against the FP32 reference |
| `tests/arch_check.py` | the capability table and the down projection's precision (16-bit below sm_80, TF32 from sm_80 on) |

The checks that need this host's other parts (they are on the other machine or need a newer card) say SKIP here:
the ones that need the safetensors checkpoints, the FP8 draft head and the GLM FP8 weights (sm_89+), the NVFP4 KV
cache (sm_90+) and the TileLang prefill (sm_80+).

## What is not done on sm_75

* the packed FP4 experts (NVFP4/MXFP4) are not decoded in hardware: the packs that need it are off;
* the W8A8 FP8 configs and the FP8 draft head are off;
* the Qwen hyper-connection mix overlap (it needs TMA) is off;
* the attention runs in the Triton sparse MLA (the FlashMLA kernel needs sm_90+);
* the BF16 dot products of the indexer and the KV compressor are emulated (their weights are BF16 upstream).
