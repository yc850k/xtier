# Turing（sm_75）适配

分支 `feat/sm75`：让 XTier 在 Turing 卡（RTX 2080 Ti / T4 一类，sm_75）上跑起来。主机例子：2× RTX 2080 Ti
（11 GB）、2× Xeon E5-2680 v4（Broadwell：只有 AVX2）、141 GiB 内存，配置见
[configs/sm75-2x2080ti](../configs/sm75-2x2080ti/README.md)。

Blackwell（sm_120）上的功能按卡的实际能力分级：[`xtier/arch.py`](../xtier/arch.py) 读一次算力等级，之后每个需要
更高等级的功能自己判断，关掉的会在日志里报一次。

## 卡上有什么

| 能力 | 等级 | sm_75 | 影响 |
|---|---|:-:|---|
| FP16 张量核（FP32 累加） | sm_70 | 有 | 内核的点积用 FP16 |
| BF16 张量核 | sm_80 | **没有** | 激活值必须是 FP16；TF32 也没有，下投影改用 16 位点积 |
| FP8 张量核 | sm_89 | **没有** | 加速包里的 FP8 功能（GLM 的 FP8 权重、DeepSeek 的 FP8 草稿头与 W8A8 配置）关闭；E4M3 的块标度改成软件换算 |
| TMA（`cp.async.bulk`） | sm_90 | **没有** | Qwen 的 hyper-connection mix 重叠内核关闭（原来就按能力判断） |
| FP4 张量核与 `cvt.rn.f16x2.e2m1x2` | sm_100 | **没有** | 热专家缓存的 FP4 解码改成软件实现；MXFP4 fused MoE（FlashInfer CUTLASS）只在 SM120 |
| 共享内存 | 每 SM | 64 KiB | GPU prefill 与 decode 的 tile 变小（RTX PRO 5000 是 100 KiB） |

BF16 与 FP8 的例子：Qwen 的 NVFP4 KV 缓存读取要用 E4M3 标度转换（sm_89 起有），所以在 Turing 上关闭；DeepSeek 的
`wo_a` 用 BF16 点积（sm_80 起有），同样关闭。

## 代码改动

- **`xtier/arch.py`（新）**：算力等级（`XTIER_ARCH` 可覆盖，给没有 GPU 的测试用）与 `has_bf16()`、`has_tf32()`、
  `has_fp8()`、`has_tma()`、`has_fp4()`、`has_blackwell_mxfp4_moe()` 等开关，以及激活值的 dtype（BF16 或 FP16）。
- **激活值的 dtype**：内核的点积操作数跟模型走（`DT`）。以前只认 BF16，现在 BF16 和 FP16 都行；Turing 上必须 FP16
  （`--dtype float16`），因为它没有 BF16 张量核，cuBLAS 也没有 BF16 GEMM。
- **CPU 引擎不变**：引擎的输入仍是 BF16（`csrc/` 一行没改）。激活值在暂存给引擎时转换（`x_h.copy_(x)`，decode
  路径是打包内核里的存储转换）。
- **`backend/prefill.py`**：`_gate` / `_down` 按 dtype 取操作数；下投影的默认精度在有 TF32 的卡上是 `tf32x3`，
  在 Turing 上是 16 位点积（`16bit`）；FP4 fused MoE 路径按能力关闭（并在日志里说明）。
- **`cache/pool.py`、`cache/prefill.py`**：`_halves` 在没有 FP4 转换指令的卡上用软件解码 E2M1（数值与硬件转换
  逐位相同：E2M1 的 8 个值在 FP16 里都能精确表示）；MXFP4 的操作数 dtype 跟激活值走。
- **`backend/fp4.py`（新）**：两种块标度的换算（E4M3、UE8M0）。E4M3 的换算指令要 sm_89，Turing 上用公式算
  （同样的数：符号位 + 4 位指数（偏置 7）+ 3 位尾数）；GPU prefill 与热专家缓存都用它。
- **共享内存**：`cache/pool.py` 的 K-tile 上限按卡的共享内存取（Turing 128，其余 256）。
- **加速包**：`xtier/packs/__init__.py` 有了 `supported(need, what)`，各包用它关掉自己跑不了的
  功能（见上面的表）；MiniMax M3.1 的包整体关闭（它的内核是 SM100 专用）。
- **`platform.py`**：SM120 的 MXFP8 调优补丁只在 SM120 注册。
- **`backend/prefill.py` 的 cudart**：按 `.13 → .12 → .11 → so` 依次找，不再写死 `libcudart.so.13`。

## 这台机器上的模型：GGUF 的 DeepSeek V4.1

`/mnt/optane/DeepSeek-V4.1-Flash/`（四个分片 + Engram 表）用 SGLang 的 GGUF 路径读：
`--quantization gguf --load-format gguf`（[configs/sm75-2x2080ti](../configs/sm75-2x2080ti/)）。

**GGUF 的专家不是 CPU 引擎能读的格式**（引擎读 NVFP4 / MXFP4），所以这些 MoE 层留给 SGLang 自己的 GGUF 内核，
XTier 的混合推理对这个检查点不生效：加载时每个层会报一次「stays with SGLang」，加载完的自检也会说
「no MoE layer uses a format the CPU engine can read」。想让 XTier 接管，需要 NVFP4 / MXFP4 的专家权重。

## GSQ 模型（Maya 打包的 GGUF DeepSeek V4.1）

`/mnt/optane/DeepSeek-V4.1-Flash/maya-ds4-gsq/` 是 Maya 打包的 GGUF 检查点：路由专家用 llama.cpp 的 IQ 量化
（每个专家一种：IQ1_M、IQ2_XXS、IQ2_XS、IQ1_S），Engram 表单独一个 GGUF 文件。

**引擎现在会算这些专家**（`csrc/engine/gsq.{h,cpp}`）：
- IQ 解码就是 llama.cpp 的 `dequantize_row_iq*`（`ggml/src/ggml-quants.c`，MIT），网格表原样拷过来，
  与参考实现**逐位相同**（四种格式各 64 轮随机块）；
- 引擎的 GSQ plan 直接读专家所在的映射文件（不复制、不分片，页留在文件的 page cache 里），
  gate/up/down 内核每次解一块 256 个值，和 FP32 激活值相乘；
- `xtier/backend/gsq.py` 读打包（`ds4.txt` 的几何、`tensors.txt` 的张量表、映射的 GGUF 文件）和每专家的量化类型；
- `tests/gsq_check.py` 用 FP32 参考对一遍（相对 L2 6.3e-3，差的是激活值的 BF16 舍入）。

**SGLang 后端也接上了**（`xtier/backend/formats.py` 的 `GsqExperts` ✓、`method.py` 的 GSQ 分支 ✓）：
- XTier 不给这层建 GPU 专家参数 ✓ → loader 跳过专家张量 ✓ → 专家永远不进显存 ✓；
- 引擎的 plan 直接指向映射的 GGUF 文件 ✓（`xtier/backend/gsq.py` ✓）；
- decode 走信箱 ✓，prefill 全部走 CPU 引擎 ✓；热专家缓存和 GPU prefill 对这个格式是关的 ✓（GPU 解不了 IQ 块 ✓）。

**还没验证的是端到端**：这台机器上跑不了这个模型（专家 157 GB，内存和显存都不够），所以 SGLang 侧只做了
单元级验证（`tests/gsq_pack_check.py` ✓：打包读取 + 引擎的 plan ✓；`tests/gsq_check.py` ✓：引擎的 GSQ 层与
FP32 参考 ✓）。SGLang 的 GGUF loader 会不会照旧把专家张量读一遍（流式，占内存峰值）✓，要真机才清楚 ✓。

## 模型的限制

专家在 checkpoint 里是 FP4（NVFP4 或 MXFP4），这由 CPU 引擎读，XTier 不重新量化。其余部分在 GPU 上跑，所以：

- 模型必须能以 FP16 跑（`--dtype float16`）：BF16 的稠密层由 SGLang 在加载时转换；
- 注意力后端要在 sm_75 上能用：FlashAttention 2 和 MLA 后端要 sm_80 起，所以要用 SGLang 的 Triton 注意力；
- 稠密层是 FP8 的 checkpoint 需要 SGLang 能按 FP16 加载。

## 验证

在 2× RTX 2080 Ti 的主机上（torch 2.13+cu130，驱动 595 / CUDA 13.2）：

- `python tests/arch_check.py`：能力判断、dtype 的选择、下投影的默认精度、各加速包功能的开关（不需要 GPU）。
- `python tests/sm75_gpu_check.py`：在卡上跑热专家缓存的 gate/up 内核（NVFP4 与 MXFP4 专家，FP16 点积，软件
  E2M1/E4M3 解码）与分组 GPU prefill（FP16 激活值），与 FP32 参考的相对 L2 误差 2.1e-4 / 2.3e-4 / 3.0e-4。
- `tools/build_engine.sh /usr/local/cuda`：CPU 引擎在这台主机上编译通过（Broadwell → AVX2 构建），一次前向的结果正常。
- 启动脚本里 FlashInfer / TileLang 的算力列表按设备取（`FLASHINFER_CUDA_ARCH_LIST=7.5`），不再写死 12.0。

没有在这台机器上做端到端的 SGLang 运行：这台机器上没有 SGLang，也没有能在 Turing 上跑的 checkpoint。
